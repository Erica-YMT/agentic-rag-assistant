# Agentic RAG Assistant 最新项目架构说明

更新时间：2026-08-12

---

# 1. 项目定位

Agentic RAG Assistant 是一个面向中文知识问答场景的 AI Agent 应用。

项目不是简单的：

用户问题 → RAG → LLM

而是一个完整的 Agent 系统，包含：

- LLM Tool Calling
- Hybrid RAG
- Corrective RAG
- Complex RAG
- LangGraph
- 短期记忆
- 显式长期记忆
- Web Search
- 并发控制
- RAG 自动评测
- Prometheus
- Grafana
- LangSmith
- Docker Compose

核心目标是让系统具备：

检索、判断、纠错、规划、工具调用、记忆、监控和部署能力。

# 3. Agent Tool Calling

核心文件：

- agent.py
- tools_config.py
- tool_executor.py
- tools.py
- client.py
- prompt.py

Agent 的基本循环：

用户问题
↓
读取聊天历史
↓
组装 messages
↓
调用 LLM
↓
模型判断是否产生 tool_calls

如果没有 tool_calls：

说明模型已经决定直接回答。

↓

生成最终答案
↓
保存聊天历史
↓
返回用户

如果有 tool_calls：

↓

agent.py 读取：

- 工具名称
- JSON 参数
- tool_call_id

↓

tool_executor.py

↓

根据 tools.py 中的 available_tools
找到对应 Python 函数

↓

执行工具

↓

工具结果以 role=tool
重新加入 messages

↓

再次调用 LLM

↓

直到：

- 模型不再请求工具
- 达到最大模型步骤
- 达到最大工具调用次数
- 检测到重复工具调用

# 4. Agent 循环保护

Agent 当前具备：

- 最大模型步骤数限制
- 最大工具调用次数限制
- 重复工具 + 参数检测
- 模型调用异常重试
- 工具已经成功时的降级返回

主要目的：

防止 Agent 出现：

模型
↓
工具
↓
模型
↓
同一个工具
↓
模型
↓
同一个工具

这种无限循环。

# 7. 为什么使用 Hybrid RAG

BM25 擅长：

- 专有名词
- 文件名
- 精确关键词
- 缩写
- 明确术语

FAISS + Embedding 擅长：

- 同义表达
- 语义相似
- 不同说法表达同一个意思

因此：

BM25
+
Embedding
+
RRF

可以同时利用：

关键词匹配能力
+
语义理解能力

# 9. Corrective RAG

项目已加入检索后证据评判与查询重写。

核心文件：

corrective_rag.py

流程：

用户问题
↓
第一次 Hybrid Retrieval
↓
Grade #1

Grade 判断：

当前检索证据是否足以回答用户问题。

如果：

sufficient = True

↓

直接返回第一次检索结果。

如果：

sufficient = False

↓

Query Rewrite

↓

模型根据：

- 原始问题
- 第一次检索结果
- Grade 不足原因

生成新的检索 Query。

↓

第二次 Hybrid Retrieval

↓

Grade #2

↓

再次判断证据是否足够。

如果足够：

返回第二次检索结果。

如果仍不足：

返回：

【知识库证据不足】

并明确要求 Agent：

不要根据不完整证据编造答案。

完整流程：

Retrieve
↓
Grade
↓
不足
↓
Rewrite
↓
Retrieve Again
↓
Grade Again
↓
Answer / Evidence Insufficient

---

# 10. Corrective RAG 的意义

普通 RAG 默认认为：

第一次检索出来的结果就是好的。

Corrective RAG 不这样做。

它会主动判断：

“我第一次到底搜对没有？”

如果没有：

重新组织查询再搜索。

因此 RAG 从：

Retrieve → Answer

升级为：

Retrieve
↓
Evaluate
↓
Decide
↓
Rewrite
↓
Retrieve Again
↓
Answer

# 12. Simple Fast Path

非常明显的短单事实问题：

例如：

“tools.py 是干什么的？”

不额外调用复杂度 Planner。

直接：

用户问题
↓
Fast Path
↓
Corrective RAG
↓
返回证据

这样可以减少：

- 模型调用次数
- 延迟
- Token 消耗

---

# 13. Complexity Planner

对于较复杂问题：

例如：

“比较 Agent Tool Calling、Hybrid RAG、
Memory 和并发控制分别怎么工作，
并说明它们之间的调用关系。”

系统先调用 Complexity Planner。

Planner 返回：

complex = true / false

以及：

subquestions

例如可能拆成：

1. Agent Tool Calling 是怎么工作的？

2. Hybrid RAG 是怎么工作的？

3. Memory 与并发控制分别如何实现？

# 14. LangGraph

复杂问题通过：

LangGraph StateGraph

组织 RAG 工作流。

LangGraph 不替代整个 Agent。

当前设计是：

Agent
↓

↓

↓

也就是说：

Agent 仍然负责：

- Tool Calling

- 模型循环
- 工具选择

LangGraph 只负责：

复杂 RAG 内部工作流。

# 15. LangGraph Send 并行 Worker

复杂问题拆成多个子问题后：

LangGraph 使用 Send

动态生成多个 Worker。

例如：

原问题
↓
拆成 3 个子问题

↓

Worker 1
Worker 2
Worker 3

并行执行：

Hybrid Retrieval

因此日志可能出现：

Worker 3 完成
Worker 1 完成
Worker 2 完成

而不是严格：

1
2
3

这是因为子问题检索是并行执行的。

# 16. Complex RAG 完整流程

用户复杂问题
↓
Complexity Planner
↓
判断 Complex
↓

↓

↓

↓
多个 Worker 并行检索

├─ Worker 1 → Hybrid Retrieval

└─ Worker 3 → Hybrid Retrieval

↓

Evidence Merge

↓

把多路检索结果合并

↓

Coverage Grade

↓

判断：

合并后的证据
是否已经覆盖原始问题。

如果：

sufficient = True

↓

把合并证据返回 Agent。

如果：

sufficient = False

↓

Corrective RAG

↓

针对完整原问题再次尝试：

检索
↓
Grade
↓
Rewrite
↓
再次检索
↓
再次 Grade

---

# 17. 为什么 Complex RAG 子问题不分别跑完整 Corrective RAG

当前设计中：

每一个 Worker
只执行原始 Hybrid Retrieval。

不会让每个 Worker 都执行：

Grade
↓
Rewrite
↓
Retrieval
↓
Grade

原因：

如果一个复杂问题拆成 3 个子问题，

每个子问题又连续调用多个模型，

一次用户请求可能产生大量 LLM API 请求。

这会增加：

- Token 消耗
- 延迟
- API 压力
- 503 / Connection Error 风险

因此当前采用：

多个子问题
↓
并行 Hybrid Retrieval
↓
合并
↓
统一 Coverage Grade

这是性能与效果之间的工程取舍。

# 20. 并发控制

项目具有两层并发保护。

## Session Lock

针对同一个 session_id。

作用：

同一会话中的多个请求必须按顺序执行。

避免：

问题 A
问题 B

同时执行导致聊天历史顺序混乱。

流程：

/chat
↓
Session Lock
↓
Agent.run()

---

# 21. Global Semaphore

除了 Session Lock，

项目还有限制整个服务同时执行多少个 Agent。

流程：

多个用户请求
↓
Global Semaphore
↓
只允许固定数量 Agent.run() 同时运行

作用：

防止大量请求同时：

- 调 LLM
- 调 RAG
- 调工具

导致：

- 上游 API 429
- 503
- CPU / 内存压力
- 整个服务失控

因此：

Session Lock

解决：

同一会话顺序问题。

Global Semaphore

解决：

整个服务总体负载问题。
